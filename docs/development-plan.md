# GitHub 到哔哩哔哩 Toy 发布工具开发方案

日期：2026-10-27  
状态：访谈决策作为产品基线保留；实现与实际验收进度见 [验收记录](verification/acceptance.md)。  
目标：交付他人仅凭文档即可独立使用的公开测试版，同时提供 Skill 帮助完成项目初始化、适配与 Action 接入。

这份方案将用户在访谈中确认的规则作为开发基线。下列技术路径、接口名称和排期记录的是方案制定时的设计，不代表当前实现状态；已发布功能和证据以[验收记录](verification/acceptance.md)及发行版为准。原始调研的版本、认证变量和平台能力记录均需绑定实际验证版本。

## 1 产品定位与成功标准

工具负责把 GitHub 上的静态网页项目接入 Toy 的预览和提审流程，使首次创建、已有作品接管、后续更新和版本追溯形成完整链路。

第一版同时服务两类用户：

| 用户 | 起点 | 第一版应达成的结果 |
| --- | --- | --- |
| 新建项目的开发者 | 有 Toy 发布资格与 GitHub 账号，尚无代码 | 从最小模板建立项目，完成构建、预览和首次提审，再完成一次更新 |
| 已有项目的开发者 | 有纯 HTML 或 Vite 前端项目 | 检查并适配项目，接入 Action，创建新 Toy 或接管已有 Toy，完成预览与提审 |

两条路径均须有不依赖 Skill 的完整文档；Skill 提供自动修改与接入能力。文档使用者无需阅读本项目实现代码，也不应必须向维护者询问缺失步骤。

成功的边界是 B 站接受提审。工作流须写明“已提交审核”，不能表示“已上线”。两条路径分别完成文档与 Skill 验收。

2026-10-28 验收方式修订：用户明确改为由 sub-agent 代替本人试用。两个不继承实现对话的代理只收到 README 的 Copy-Paste Prompt 和各自场景，分别从零创建俄罗斯方块小游戏，以及适配真实已有项目 `muzzle-device-lab`，完成 GitHub 推送、真实 Toy 预览与提审，并记录卡点。此项替代原“至少一名未参与实现的人按文档独立跑通”的要求；结果按代理验证记录，不称为人类试用。

方案制定时沿用原材料中的项目标识 `drdavid-kor/bilibili-toy-deploy`、MIT 许可和中英 README；当时远程仓库与版本尚未创建。现已有[公开仓库](https://github.com/drdavid-kor/bilibili-toy-deploy)；发行版本与实际验收见[验收记录](verification/acceptance.md)。市场规模、付费意愿和官方合作均不作为已验证前提。

## 2 已确认的产品决策

| 编号 | 开发基线 |
| --- | --- |
| D01 | 第一版为他人可独立使用的测试版，允许用户手动更新过期凭据。 |
| D02 | GitHub 托管 Runner 必须可用。自备 Runner 仅作为可选方案，不能代替默认路径的验收。 |
| D03 | 接受实验性的登录态注入，但必须实测可用，披露限制，并独立封装认证逻辑。 |
| D04 | 自动保存 Toy 关联，优先使用 GitHub Deployment 记录；用户授予部署记录写权限，无须另配 GitHub 长期令牌。异常时支持手动补填 Toy ID。 |
| D05 | 发布 GitHub Release 自动提审，另保留手动入口。推送 tag 本身不提审。 |
| D06 | 主分支更新后自动生成 Toy 预览，也支持手动生成。所有 PR 默认只构建和预检。 |
| D07 | Release 默认复用同一提交已生成预览的构建包。没有可用包就停止，提示先生成预览。 |
| D08 | 用户可手动覆盖 D07，为指定 Release 的确切提交重新构建并直接提审；须记录覆盖行为与操作者。 |
| D09 | 前一个版本仍在审核时，允许新版本提审，由 B 站接受或拒绝；同一 Toy 的写操作仍串行执行。 |
| D10 | 首次创建默认仅链接可访问；更新保留已有可见性，除非用户显式执行元信息同步。 |
| D11 | 未有已保存关联时，核对账号并完整查询 slug。唯一匹配自动接管；确认不存在才创建；查询失败或匹配不唯一时停止。 |
| D12 | 首次创建使用仓库元信息。日常发布只更新作品包；元信息仅在单独手动触发同步时覆盖，并只处理显式填写字段。 |
| D13 | 提审被接受即为工作流成功，不自动追踪审核结果。 |
| D14 | 用户在工作流配置构建命令。Action 接收产物目录，不自动猜测构建方式。 |
| D15 | 请求已发出但提审结果不明时，停止自动重试，显示“结果待核实”，由用户核实后决定是否重试。 |
| D16 | Skill 属于第一版，允许修改项目代码与配置；需要后端迁移、登录替换、存储重做等架构变更时，说明影响并停止确认。 |
| D17 | 完整支持纯 HTML/CSS/JS 和 Vite，包括 React、Vue。其他框架先检查兼容性，不承诺自动完成适配。 |
| D18 | 从零创建只建立可运行的最小项目并接入发布流程，不承担根据创意实现完整业务功能的职责。 |

## 3 第一版交付范围

交付一个单 Toy 的发布 Action、一套共享规范和两种接入方式：文档手动接入、Skill 辅助接入。

### 3.1 必须交付

- Composite Action 入口及可测试的内部脚本，封装官方 CLI，不直接调用未公开的 Toy HTTP 接口。
- 纯 HTML 最小模板，Vite 最小模板与 React、Vue 的接入示例；明确构建命令与输出目录。
- 预检、创建或接管、预览、产物保存、Release 提审、手动覆盖提审、单独元信息同步。
- Deployment 关联读写、跨运行恢复、串行写入、重复触发检查和结果不明处理。
- 中英 README、两条快速上手指南、配置参考、凭据配置与更新指南、故障排查、实验性限制说明。
- 可安装 Skill、安装说明、可复制的调用示例，以及与 Action 共用的配置规范、模板和验收清单。

### 3.2 不纳入第一版

审核轮询与通知、PR 上传预览与评论机器人、多 Toy 矩阵、GitHub App、Cloudflare 中继、凭据托管、视频绑定、任意框架自动构建、后端迁移，以及从创意生成完整业务应用。

不承诺固定的 session 寿命、审核时长、自动刷新凭据或发布成功率。CLI 的版本和静态检查通过，也不等同于页面已经在 Toy 环境正常运行。

## 4 两条快速上手路径

### 4.1 从零创建

1. README 首屏提供“新建 Toy 项目”和“接入已有项目”两个入口，并说明 Toy 发布资格、GitHub 权限及实验性认证前提。
2. 用户复制最小模板到自己的新仓库。默认纯 HTML；已有框架偏好时选择 Vite 示例。不能要求用户复制整个 Action 开发仓库。
3. 用户填写 slug、首次创建元信息和作品目录。以明确文件记录配置，凭据不写入文件。
4. 按图文或逐步说明完成官方登录，把经验证可导出的会话安全存入仓库 Secret；设置示例所需的工作流权限。
5. 主分支工作流构建并预检，生成预览，保存同一份构建包，Summary 提供查看方式和下一步。
6. 用户查看预览，为对应提交发布 Release；工作流创建 Toy 或按唯一 slug 接管，然后提交同一构建包并保存 Toy ID。
7. 用户修改示例、再次预览和发布 Release，验证后续走更新路径且没有重复创建。

首次预览可能只返回预览链接、不产生已创建的 Toy ID。该阶段可保存账号、slug 和产物关联，不能虚构 Toy ID；正式创建与 ID 保存发生在平台实际返回 ID 后。具体行为由 P0 验证。

### 4.2 接入已有项目

1. 识别入口、包管理器、现有构建命令、输出目录和已有发布流程。
2. 检查是否能输出静态文件，列明资源基路径、路由、远端接口、认证和存储依赖。
3. 对 HTML 或 Vite 执行必要适配，保留业务功能与现有工程结构。不能仅凭正则检查就宣称兼容。
4. 接入配置和工作流，保留项目原有测试与其他部署流程。
5. 新 Toy 配置 slug；已有 Toy 可显式填 ID，也可按当前账号与唯一 slug 自动接管。
6. 完成构建、静态预检、页面验证和 Toy 预览，然后按 Release 流程提审。
7. 输出改动清单、验证结果、未解决限制，以及后续发布和恢复方法。

文档应分别说明 hash 路由、多页面、动态导入、字体与图片路径、浏览器存储及已有外部 API 的检查方法。不得通过删除功能或把网络请求改成模拟数据来“通过适配”。

## 5 事件与操作规则

以下为产品行为矩阵，事件参数与权限需在 P0 后固化到可运行示例。

| 入口 | 构建与检查 | Toy 操作 | 结果 |
| --- | --- | --- | --- |
| PR，包括同仓库及 fork | 构建、预检 | 无上传、无提审 | 检查结果 |
| 主分支 push | 按用户配置构建、预检 | 生成预览 | 预览记录与固定构建包 |
| 手动预览 | 为选定且受信任的提交构建、预检 | 生成预览 | 同上 |
| Release published | 查找并校验对应提交的预览产物，不重新构建 | 创建或更新并提审 | 已提交审核，或明确的停止原因 |
| 手动常规提审 | 选择 Release，校验对应预览产物 | 同上 | 同上 |
| 手动覆盖提审 | 明确指定 Release，解析到提交，再构建和预检 | 直接提审 | 标注未复用既有预览产物 |
| 手动同步元信息 | 校验配置和关联目标 | 独立元信息提审 | 同步字段、目标和提审结果 |
| tag push | 无独立发布动作 | 无 | 避免与 Release 重复触发 |

建议示例用 `release: published`，默认排除 prerelease；需发布预发行版的用户可显式调整。首次公开测试不订阅 deployment 或 deployment_status 事件触发 Toy 提审，避免状态记录形成循环。

所有提审及元信息同步共用单 Toy 写入锁。预览可以取消尚未上传的过时构建；已经发出的写请求不能靠取消 Runner 当作平台已撤销。不能取消正在提审的任务来实现“新版本覆盖旧版本”。

同一 Release、相同包摘要、相同操作的成功记录用于防止重复触发。不同 Release 即使前次仍在审核也允许提交。相同提交的不同构建包不能被误判为同一次发布；用户明确重提或覆盖必须记录新尝试。

## 6 产物与 Release 的对应关系

### 6.1 预览记录

建议每次有效预览保存以下非敏感信息：仓库 ID、完整 commit SHA、工作流及 run ID、run attempt、artifact ID、文件包 SHA-256、CLI 版本、预检版本、目标 slug、目标账号的非凭据标识、预览创建时间和配置摘要。

保留实际上传给 Toy 的固定包；如 CLI 只能接受目录，需证明恢复后的文件内容与预览时一致。缓存仅用于加速依赖和 CLI 下载，不作为唯一发布产物来源。

预览凭据、会话和访问密码不得进入 artifact。预览 URL 若包含访问令牌，不能未经核实写进公开 Summary 或 Deployment；P0 需确定安全展示方式。

### 6.2 默认提审

Release tag 解析为完整 commit SHA。仅使用本仓库受信任工作流为该 SHA 生成、预检通过且成功预览的产物，校验目标关联与包摘要。不能只匹配 artifact 名字，不能使用 PR 工作流上传的包，也不能直接选择最近一次成功运行。

如果同一 SHA 有多次预览，按受信任运行和明确 artifact ID 选择，Summary 显示选中的运行与摘要。若目标账号、slug 或首次创建所需配置发生变化，要求重新预览或显式覆盖。

artifact 已过期、被删、下载失败、摘要不符或缺少预览成功记录时，停止常规提审。建议产物默认保留 30 天并允许配置，实际受仓库和组织限制；README 明确过期后的重新预览方法。[S7]

### 6.3 手动覆盖

提供明确命名的覆盖入口，展示目标 Release、解析后的 SHA 和“重新构建后直接提审”提示。默认不勾选覆盖，不从普通 Release 失败自动转入覆盖。

覆盖只跳过“必须已有预览产物”要求，不跳过预检、目标账号与关联校验、写入锁和结果不明保护。使用目标 Release 的配置和源码，不能静默构建当前主分支。新包在发送前保存并计算摘要，记录操作者、run ID、触发方式和重建事实。

建议默认仅允许受保护主分支历史中的 Release 提交；放宽来源属于使用者的显式配置，不能让不受信任的提交访问发布凭据。

## 7 Toy 关联与恢复

### 7.1 关联解析顺序

1. 若显式提供 Toy ID，验证归属和预期 slug；与已有记录冲突时停止，不静默改绑。
2. 否则读取本仓库、本项目的 Deployment 关联，验证 schema、当前账号、slug 与平台归属。
3. 无有效关联时，通过官方 CLI 完整分页查询当前账号的 Toy。
4. slug 唯一匹配则自动接管并保存；零匹配且查询完整成功才允许创建；多匹配或查询异常停止。
5. 已知创建或提交结果不明时，查询用于核实与恢复，不因暂时看不到对象就自动再创建或提审。

自动接管会影响已有作品，快速上手页须在填写 slug 的步骤直接说明该行为；不再增加逐次手动确认。日常内容更新不能附带仓库里的标题、封面或可见性参数。

### 7.2 Deployment 保存设计

采用独立 task/environment 命名区分关联、预览和提交记录；记录含 schema 版本、项目键、账号标识、Toy ID、slug、SHA、包摘要和运行来源。此处是拟定的数据设计，须验证 API 实际读写和权限。[S5][S6]

以记录追加方式保留关联历史，查询时筛选并校验当前有效记录；不依赖“最后一条 Deployment 就是目标”。完整分页、不同记录类型、删除记录、账号切换和跨运行读取均须覆盖。

使用工作流临时 `GITHUB_TOKEN`，按 job 配置 `contents: read`、`actions: read`、`deployments: write` 等必要权限。权限不足应在平台写操作前发现。不要为保存 ID 要求用户新增长期 PAT，也不要改成自动写回默认分支。[S5]

平台已接受提审而 Deployment 写入失败时，Summary 区分“提审已接受”和“关联保存失败”，输出不含凭据的 Toy ID 与恢复步骤。恢复关联本身不得再次提审。

Deployment 仅保存可公开的非敏感记录；公开仓库的部署记录不能当作私密存储。账号标识仅保存校验所需最小字段。预览链接和完整 CLI 原始响应需先脱敏再决定是否保存。

### 7.3 状态语义

应用内部区分：预检失败、已生成预览、缺少预览产物、已提交审核、平台明确拒绝、结果待核实、关联保存失败。

工作流 success 表示本次请求被接受。若使用 Deployment success 表示提交成功，必须采用明确的 `toy-submission` 非生产环境及“已提交审核”描述，不能把正式线上地址标为此次版本已部署。第一版不推断审核通过，也不轮询。

## 8 元信息与配置契约

方案制定时建议使用可校验的数据配置文件；当前已确定为 `toy.config.json`，区分目标信息、首次创建参数与可手动同步字段。可执行字段和示例见[配置说明](configuration.md)及[JSON Schema](../schema/toy.config.schema.json)，本节保留设计语义。

| 配置类别 | 语义 |
| --- | --- |
| slug 与可选 Toy ID | 目标解析和恢复依据；更新不尝试修改 slug |
| 作品目录 | 用户工作流构建后的目录；Action 不负责猜测构建命令 |
| 首次创建元信息 | 标题、分类、图片等按锁定 CLI 支持范围提供；可见性缺省为 link-only |
| 元信息同步字段 | 仅手动同步时使用显式字段；省略即保留，空值不自动等同于删除 |
| CLI 版本 | 默认锁定实际验收通过版本；不直接把原材料中的 v0.6.4 当作已验证基线 |
| 凭据 | 仅来自 Secret/环境注入，不存入配置文件 |

常规更新必须验证 CLI 省略元信息时确实保留平台值。若 CLI 默认值会覆盖可见性等字段，需要兼容处理，并在 P0 阶段验证；不能只靠“不传参数”假定满足用户决定。

手动元信息同步独立于包体发布，不要求包体预览产物，但入口明确提示“即将提交审核”。只对 CLI 支持字段实现，图片内容与最终字段在运行记录中可追溯。若涉及访问密码，应通过 Secret 单独注入，不得写入公开配置和记录。

## 9 认证、依赖与失败处理

### 9.1 认证

实验性认证适配层负责：临时会话目录或环境注入、账号检查、过期分类、日志脱敏和运行结束后的清理。方案制定时，原材料提到的 `TOY_CLI_SESSION_TOKEN` 等变量只是待验证候选；当前用户仓库 Secret、CLI 注入方式与限制见[认证说明](authentication.md)，不把它们称作官方 CI 接口。[S2]

README 必须给出普通用户可复现的“本地官方登录 → 安全导出或读取会话 → 设置 GitHub Secret → 测试 → 过期更换”流程。如果无法提供清晰、安全的凭据取得方式，即使维护者能让 CI 跑通，也未通过公开测试门槛。

不得要求用户把凭据粘贴到聊天、issue 或日志中。构建阶段不注入 Toy 会话，发布阶段只使用已构建产物，避免把秘密暴露给依赖安装脚本。设置日志遮罩不能替代不执行不受信任代码。[S4]

### 9.2 CLI 与预检

固定 CLI 版本并验证下载完整性；固定预检脚本来源和版本，保留许可与上游提交信息。建议随 Action 携带同一固定版预检脚本，避免运行时下载与备用版本行为不同；如保留原材料的下载后备策略，两份必须校验为相同内容。

使用 `--help-json` 验证当前所需命令和参数，并以记录的成功与失败样本校验响应解析。预检 ERROR 阻止发布，WARN 写入 Summary。官方脚本目前区分入口 HTML 体积限制和其他体验警告，实施时使用锁定版本规则，不自行混合严重程度。[S1][S3]

### 9.3 重试与恢复

| 情况 | 行为 |
| --- | --- |
| 下载、只读查询的暂时错误 | 有上限的退避重试，明确退出原因 |
| 身份失效、权限不足、参数或预检错误 | 不盲目重试，给出修复步骤 |
| 可证明请求尚未发出的传输失败 | 可有限重试，必须有可判定依据 |
| 请求已发出、客户端超时或响应无法解析 | 标为结果待核实，停止自动写入重试 |
| 平台明确拒绝提审 | 显示平台原因；允许用户修复后重新触发 |
| 提审成功但本地记录失败 | 恢复记录，不重提；保留平台成功与记录失败两种事实 |

用户人工重试前需看到原请求的 SHA、包摘要、Toy ID/slug、时间及结果不明提示。缺少原记录时不能默认为从未提交过。

当前实现仅对 CLI 安装下载、`whoami` 与 `mylist` 的暂时错误做最多三次尝试；身份、业务、用法和永久下载错误不重试。预览、创建、更新等 Toy 写请求均不自动重试。运行 Summary 输出经过筛选的操作上下文，帮助核对所选产物与恢复原请求；预览上传前先确认 GitHub 记录可写。beta.3 的发行验证状态见[验收记录](verification/acceptance.md)。

## 10 Skill 的第一版规格

建议提供一个 Skill，入口先判断新建还是改造，内部复用同一套模板和检查清单。Skill 的实现遵守安装环境的权限与用户指令，不另建独立的 Toy 发布协议。

### 10.1 新建模式

检查目标目录，避免覆盖已有项目；选择纯 HTML 或 Vite 最小模板；填入配置并生成工作流；解释每个事件；引导用户配置凭据；在有授权和工具能力时完成仓库接入与预览验证。只有创意时止于可运行模板和发布接入，业务实现可由编程助手在其他任务中继续。

### 10.2 改造模式

先阅读项目约定和现有代码，识别构建、路由和依赖，列出必要修改；在用户接入请求范围内直接完成常规适配与工作流接入。不得覆盖无关改动、重写整个应用或删除核心功能。

涉及后端迁移、登录系统替换、存储重做时，给出原因、影响和可选方案，停止依赖该决策的修改，待用户确认。其他框架输出兼容性判断，不冒充完整支持。

### 10.3 安装与调用体验

仓库包含可发现的 `skills/<skill-name>/SKILL.md`、模板引用和两条路径的操作说明。公开发行时验证实际安装命令、目标宿主可发现性和更新方式；仓库与版本尚未发布时，文档不能声称安装命令已可用。

README 提供两种自然语言调用范例：“初始化一个 Vite 项目并接入 Toy 发布”和“将当前项目适配为 Toy 并接入发布 Action”。明确 Skill 可修改文件、所需工具，以及缺少 GitHub 写权限时如何完成本地准备和交接。

Skill 能引导配置和验证，但不能声称已替用户获得 Toy 发布资格。创建远程仓库、推送工作流、写入 Secrets 和触发提审按用户实际授权执行，不能把本方案视为未来任意用户的授权。

### 10.4 Skill 验收

一次新建和一次已有项目适配，分别检查：最小项目可运行、实际构建成功、必要路由和资源可访问、配置正确、工作流事件符合本方案、凭据未泄露、预览验证结果真实。至少包含已有路由的 Vite 项目，以及需要架构改造时正确停止的样例。

Skill、README 与 Action 的字段、模板版本、默认事件和错误处理必须一致。CI 可检查共享示例和 schema，不能让 Skill 靠复制一份旧说明长期漂移。

## 11 开发前技术验证门槛

P0 原计划使用隔离的测试仓库与有权限的测试 Toy。下列保留原验证标准；各项已执行的结果、未覆盖边界及证据见[验收记录](verification/acceptance.md)。

| 编号 | 验证问题 | 通过标准 | 不通过时的处理 |
| --- | --- | --- | --- |
| G1 | 实验性会话能否用于托管 Runner | 普通用户可配置；至少两个全新运行可查询身份并完成所需操作，另做跨时间观察并记录间隔 | 不发布公开测试版；自备 Runner 不能代替通过 |
| G2 | 如何失效与更换会话 | 验证过期/无效凭据错误、重新配置后的恢复；记录本地重新登录/登出的影响 | 修正说明和适配；不承诺未观察到的寿命 |
| G3 | CLI 的创建、预览、更新与接管语义 | 留存脱敏样本；确认预览是否创建对象、ID 返回时机、分页与 slug 匹配、归属验证 | 调整实现；无法唯一关联时阻断写入 |
| G4 | 默认保留平台元信息 | 更新包体不改变标题、封面、分类和可见性；手动同步只改选中字段 | 修正兼容层后再进入发布验收 |
| G5 | Deployment 关联存储 | 默认临时令牌读写成功，跨运行读取正确；删除、分页、冲突和记录失败可恢复 | 查明限制；不静默改为新增 PAT 要求 |
| G6 | 预览包复用 | 同一 SHA 对应固定 artifact，下载后摘要一致，提审确实使用该包；缺失和篡改被拦截 | 修复后才开放默认 Release 提审 |
| G7 | 写请求与重试边界 | 模拟超时和异常响应，不重复创建/提审；明确返回成功、拒绝或未知 | 未知分支默认停止，补足恢复路径 |
| G8 | 权限与链接可见性 | fork PR 无发布权限；发布 job 不执行不受信任构建；预览 URL 和记录可安全展示 | 调整隔离与输出位置后再验收 |

半天可以完成一次连通性检查，不能证明会话长期稳定。记录每项使用的 CLI 版本、Runner、日期、实际观察间隔和脱敏证据。此处保留开发前门槛；各项实际证据与当前状态以 [验收记录](verification/acceptance.md) 为准。

## 12 开发顺序与工作量

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| P0 技术验证 | 执行 G1–G8，冻结 CLI 版本、响应样本、认证配置方式和关键存储设计 | 关键路径成立，未知项有明确边界，无阻断默认托管 Runner 的问题 |
| P1 发布核心 | 配置校验、CLI 适配、预检、目标解析、关联恢复、串行写入、状态与错误分类 | 核心成功路径及失败恢复测试通过 |
| P2 事件与产物 | PR 检查、主分支预览、Release 复用、手动覆盖、元信息同步 | 事件矩阵逐项通过，固定包与提交关联可追溯 |
| P3 快速上手 | 纯 HTML/Vite 模板、React/Vue 接入示例、中英 README、指南和 Skill | 两类用户都能完成接入；Skill 不扩大适配范围 |
| P4 公开测试验收 | 真实路径验证、非作者试用、问题修复、许可与发布准备 | 本节和下一节标准全部满足，形成可审阅的测试版发布内容 |

估算：技术探索约 1–2 人日，另有跨时间观察；核心与工作流约 5–8 人日；文档、模板、Skill 与外部试用修正约 3–5 人日。合计约 9–15 人日有效工作量，P0 后重估。该估算包含新增上手与 Skill 范围，不沿用原材料 2–4 人日的薄封装估算。

本节记录原开发顺序。发行版本与按修订标准进行的独立代理试用状态见[验收记录](verification/acceptance.md)。
